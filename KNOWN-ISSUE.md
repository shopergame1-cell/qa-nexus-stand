# Відомий дефект: Maven-деплой у CI (TASK-55.1)

## Що працює (перевірено в CI, прогін за прогоном)

| Крок | Стан |
| --- | --- |
| Nexus піднімається в Docker | ✓ |
| Три репозиторії створюються (`qa-releases`, `qa-central`, `qa-public`) | ✓ |
| Автентифікований **запис** у `qa-releases` через curl | ✓ (це і є перевірка пароля) |
| Maven **читає** залежності зі стенда (шлях читання анонімний) | ✓ |

## Що не працює

`mvn deploy` у CI отримує **401 Unauthorized**, хоча:

- Maven надсилає саме Basic auth і саме тим користувачем: у логах `Using connector BasicRepositoryConnector ... with username=admin, ***`;
- той самий пароль через `curl -u admin:... -X PUT --upload-file` у тому самому кроці **приймається** (перевірено пробним записом).

Тобто код стенда тут ні до чого — різниця саме в тому, як Maven-деплой розмовляє з Nexus.

## Що вже виправлено на шляху до цього (кожна з цих речей була справжньою)

1. `PluginResolutionException` — mirror на `central` ламав саму збірку. Прибрали: плагіни беруться з Central напряму.
2. Maven 3.8+ блокує http-репозиторії — додано дозвіл (`maven-default-http-blocker` зі `blocked=false`).
3. Двокрапка в назві кроку ламала YAML workflow — перейменовано.
4. **Nexus 3.70 не бере пароль адміністратора зі змінної середовища** — він генерує його у `/nexus-data/admin.password`. Бутстрап переписано: читаємо файл і зводимо пароль до пароля стенда.
5. **Читання списку репозиторіїв доступне анонімно** — перевіряти пароль читанням не можна, це хибний позитив. Перевірка переведена на запис.
6. **Анти-брутфорс Nexus блокує IP після кількох невдалих входів** — спроби «вгадати пароль» роблять гірше: далі 401 приходить навіть із правильним паролем. Тому всі вгадування прибрано: бутстрап детермінований.
7. Деплой переведено на **окремого сервісного користувача** (`qa-deploy`, роль `nx-admin`) замість адміністратора — це і безпечніше.

## Що робити далі (наступні кроки, коли буде час)

1. Забрати повний лог кроку деплою з артефакта прогону (`maven-logs`) або з UI і знайти, що саме Maven шле не так (у логах видно 401, але не видно тіла відповіді Nexus — воно пояснило б причину).
2. Спробувати `-Dmaven.resolver.transport=wagon` (класичний транспорт замість рідного) — у workflow вже є гілка для цієї спроби.
3. Перевірити локально: підняти стенд через Docker і виконати `mvn deploy` руками — якщо локально проходить, дефект специфічний для CI-середовища (наприклад, поведінка проксі раннера).
4. Як тимчасове рішення для перевірки стенда в CI — публікувати артефакт через curl (перевірка запису вже працює), а Maven лишати лише для шляху читання.

## Чому це не «просто додати пароль»

Спокуса — вписати пароль у `settings.xml` і забути. Але стенд навчальний: студент має пройти той самий шлях, що в реальному проєкті, де пароль шифрують і не тримають у git. Тому пароль живе лише в файлі `.nexus-password` (у git не потрапляє), а `settings.xml` у прикладах містить плейсхолдер-пояснення.
